# Per-component bottleneck matrix under resource pressure

Bead: mayor-lewl1.2
Date: 2026-11-05

**Answer: on a 1 GiB / 1 vCPU node the only pressure type with observed data is memory, and its failure is one shared mechanism (no anon headroom, so every component's code pages are evicted and refaulted); the shipped defaults leave every upstream protection (kubelet eviction, allocatable enforcement, kubepods cap) effectively inert, and the u7s-owned loops that amplify pressure are few and cheap to bound (scheduler watch reconnect/relist at a fixed 5 s, 30 s non-backoff-gated resync, no request timeouts) while the dominant amplifier is upstream behaviour u7s does not tune (NotReady -> unreachable taint -> pod eviction -> controller re-creation).**

## The shared mechanism (observed)

- With no swap only file pages are reclaimable. Pods' anon is paid for by evicting file cache; control-plane `Pss_File` goes to ~0 and refaults (6bw98/36soz via #2117, Lima n=1; `memory-management-state.md` "Evidence for the mechanism").
- Symptom is platform dependent: GCP pd-standard = ~95% iowait (ltido); Lima = ~100% sys CPU with iowait ~0 and Node Ready/API up (lt2nh live check, "20-pod step stalled at 1/20 for 600 s with node Ready, API up, iowait ~0, sys CPU ~100%"). So "CPU on 1 vCPU" and "IO" are not independent pressure types on this node: both are the reclaim/refault loop seen through the platform's storage.
- Per-pod steady cost is <1 MiB (e5idl: slab 0.19-0.21, conmon 0.13, pause 0.04); the wedge cost is transient refault: GCP 10->20 pod ramp 207 s with ~4 GiB of page-cache refaults, Lima 1 s (e5idl). Lima refault rate ~200x GCP's (g28ic).
- Pre-burst headroom predicts the knee regardless of arm (9ygmh); trimming ~60-70 MiB moved a 50-pod burst from wedge to PASS in 6 s (#2115 live, n=1, code also changed).
- Userspace responders cannot act on a starved node: j1ao0 arm D, "node went Unknown/unreachable at +181 s, before kubelet could act"; zero `Evicted` events, no MemoryPressure taint, kernel OOM killer did fire but only against pods (adj 1000/730/927), never the control plane.

Amplification inside this component: **watch lag -> relist.** A starved apiserver serves slow consumers, the 1024-slot broadcast lags (`sqlite.rs:2631-2650`), recovery rescans the ring while holding its read lock on a tokio worker, and if the 512-slot ring has compacted past the client it yields `Compacted` (410) and the client relists. Cost grows with exactly the pressure that slows the consumer. Observed-in-source, not observed under overload (no `WATCH_BROADCAST_LAGGED_TOTAL` sample in the evidence). Mitigation: nothing u7s-side beyond ring sizing (`RING_CAPACITY` 512 was chosen to save memory: stale clients get 410; the memory-state doc says a full conformance run needed 25 replayed events) - conformance-safe, but trading memory for relist cost; decide only with a measurement.

## Pressure types with no observed data

- **Disk space / image GC**: no run in the evidence touches `nodefs`/`imagefs` thresholds. All D rows are inferred from kubelet defaults and the epic's k3s cited behaviour. A cheap experiment (fill `/var/lib/containers`, watch kubelet GC CPU on 1 vCPU) is the missing evidence.
- **CPU-only starvation (no memory pressure)**: the only CPU-bound case in the evidence is the e2-micro run (hjwdo description: "Not CPU-bound, unlike the e2-micro run" - the e2-micro data is not in the local sources I read). Lima's "sys CPU ~100%" is reclaim, not independent CPU contention.
- **Swap**: observed positive (zram) but pre-dates the current `OOMScoreAdjust`, trim, and gate changes (2026-10-16); retest before relying on it for the gate.
