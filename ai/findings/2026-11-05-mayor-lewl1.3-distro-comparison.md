# kubeadm / k3s / k0s: protecting system components under resource pressure

Bead: mayor-lewl1.3 (parent epic mayor-lewl1)
Date: 2026-11-05

**Answer: the mayor's recollection is mostly right but incomplete.** None of
the three set systemd `MemoryLow`/`MemoryMin`/`CPUWeight` on any control-plane
unit, and none reserve memory by default. kubeadm and k3s do protect the
control plane by `oom_score_adj` (kubeadm: -997 via node-critical static pods;
k3s: the whole process at -999 via the embedded kubelet), k0s does not, and
two corrections matter: (1) k3s drops the default `memory.available<100Mi`
hard eviction; (2) in 1.37 `MemoryQoS` is Beta and **default-on**, so
kubelet writes `memory.min`/`memory.low` for pod cgroups only, which tilts
reclaim toward pods and away from any host-level control plane (u7s).

Pinned versions (all fetched with `gh api` at the tag, cached in
`temp/research/`): kubernetes `v1.37.2` (kubeadm), k3s `v1.37.2+k3s1`, k0s
`v1.37.2+k0s.0`. Upstream `release-1.37` kubelet defaults are the same code
all three embed.

## Mayor's recollection, checked

- "None protect control-plane file pages by default": **holds for all three.**
  No `memory.low`/`memory.min` on any control-plane cgroup or unit. kubeadm
  static pods are Burstable (CPU request only, `manifests.go` L70-108) and
  get QoS-class `memory.low` only as part of the aggregate Burstable
  requests.
- "kubeadm enforces pods allocatable but with empty reservations": **holds**,
  and applies equally to k3s, k0s and u7s (shared kubelet default).
- Not recalled: k3s memory-eviction gap; k3s/kubeadm `oom_score_adj`
  protection; MemoryQoS default-on in 1.37; k0s `kubeReservedCgroup` set
  but inert.

## What u7s could adopt or do better

1. **Raise the real protection, not the oom score.** All three stop at
   `oom_score_adj`; u7s already matches kubeadm there. Nobody sets
   `MemoryLow`/`MemoryMin` on the control plane, so there is no prior art to
   copy. The u7s #2039 MemoryLow-only A/B showed no knee shift; the
   untested lever is `memory.max` on `kubepods.slice` (experiment E).
2. **`enforceNodeAllocatable: pods` with real `systemReserved`.** The
   upstream default already sets `memory.max` on `kubepods.slice` to
   allocatable; only the reservation is missing. Setting
   `systemReserved.memory` (and `kubeReserved`) makes the kernel cap pods
   below capacity so the host control plane keeps headroom. This is the
   kubeadm-documented knob and Conformance-neutral. Verify the
   `system-reserved`/`kube-reserved` cgroup enforcement path separately:
   enforcing them also writes `memory.min` on that cgroup under MemoryQoS
   (`node_container_manager_linux.go` L171-179), which could give the
   control plane `memory.min` if u7s units are placed in the reserved slice.
3. **Keep memory.available hard eviction (do not copy k3s).** k3s's
   eviction override has no memory signal, which is the opposite of what
   graceful degradation needs. Consider raising it above 100Mi for 1 GiB
   nodes (for example 150-200Mi plus a soft threshold) so eviction triggers
   before the page-cache wedge. Earlier "early eviction" test starved the
   kubelet (mayor-j1ao0), so pair with a protected kubelet.
4. **MemoryQoS is on and biased toward pods.** Decide deliberately:
   disable `MemoryQoS` (a one-flag change in `kubelet_round2_flags`) so
   host-level control-plane pages are not reclaimed ahead of pod pages, or
   keep it and put control-plane units into a protected slice. This is an
   effect specific to u7s's host-process layout; kubeadm control plane pods
   live under kubepods and share the protection.
5. **Give u7s kubelet/CRI-O the same unit-level protection.** Only
   apiserver and KCM have `OOMScoreAdjust`; the kubelet sets itself -999 but
   CRI-O and `kubelet.service` carry no unit-level setting.
6. **Pin pause image against image GC** (k3s#14923 class) and test image-GC
   under disk pressure; none of the distros is a model here.

Evidence not obtained: kubeadm's packaged `10-kubeadm.conf` drop-in
(distro packaging, outside k/k); k3s kswapd/image-GC storm reports; runtime
confirmation of the k3s process-level -999 (inferred from source).
