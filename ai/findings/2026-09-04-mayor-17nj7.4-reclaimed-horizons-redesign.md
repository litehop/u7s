# reclaimed_horizons redesign (2026-09-04)

Bead: mayor-17nj7.4

Status: audit findings, no code changed. Scope: `crates/store/src/sqlite.rs`
(`reclaimed_horizons`, `preserve_reclaimed_horizon`, `find_reclaimed_horizon`,
`get_or_create_shard`) and its one caller,
`crates/apiserver/src/handlers/watch.rs:803`.

**Answer: PR #1556's three attempts all fail for the same structural reason —
they fold an evicted entry's floor into ANOTHER map key (a parent prefix),
and a parent key can be novel, so the map does not shrink. Replace the
fold-into-a-key scheme with fold-into-a-single-global-`AtomicU64`: cap the
map at N entries, and on eviction `fetch_max` the victim's horizon into one
process-wide overflow value instead of inserting anywhere. Lookup becomes
"exact key, then one-level-parent key, then the atomic" — three O(1) steps,
never a scan — and correctness (never under-report) holds unconditionally
because the atomic is an unconditional last-resort fallback, not a hierarchy
that specific future queries must happen to walk into.** This closes every
failure mode the three attempts hit, at less code than any of them.

---

## 1. The invariant that must hold

`compaction_horizon_for(prefix)` (`sqlite.rs:470`, called from
`watch.rs:803` on every watch-open) must never return a value **lower**
than the true discarded-history floor for `prefix`. Under-report → a
reconnect with a genuinely stale `from_revision` is told it is caught up
and silently skips events it should have replayed (data loss, not a
crash). Over-report is always safe: worst case is a spurious 410 telling a
client to re-list, which every client already handles.

So any bounding scheme is free to lose **precision** (report a higher
floor than the true one for a specific abandoned prefix) but must never
lose **soundness** (report lower than true, or 0 when a floor was known).

## 2. Why every attempt broke it

The current unbounded design (`sqlite.rs:266-284`, `928-938`, still on
`main` — PR #1556 never merged) keeps one exact `HashMap<String, u64>`
entry per torn-down shard key forever, found by an O(n) scan
(`find_reclaimed_horizon`) that filters `prefix.starts_with(shard)` and
picks the longest match. Root cause of the leak: a namespace-scoped watch
prefix is never reused (each namespace name is normally created once), so
its entry is immortal; only resource-type-root entries get reused (via
`get_or_create_shard`'s exact-match `remove`).

All three PR #1556 attempts kept the "evict one entry, but don't just
discard it — fold its value into another map key" shape, and each broke a
different way:

- **Round 1 (naive discard-on-evict, implied by the bug's own opening
  description):** evicting simply removed the entry. A later query for
  that exact evicted prefix hit nothing → `find_reclaimed_horizon` returned
  0 → under-report. Rejected before merge.
- **Round 2 (fold into parent, protect the parent only while a live
  namespace sibling references it):** a resource type watched only
  cluster-wide (all-namespaces) has a **childless root** — no namespace
  sibling ever exists to protect it — so the root itself was evictable.
  Its fold landed one level *above* the root (a group-level key), but
  `find_reclaimed_horizon`'s single-level fallback from a namespace query
  under that type only ever checked the root, never the group-level key
  two hops up → 0 → under-report. Caught by critical-reviewer, reproduced
  with `MAX_RECLAIMED_HORIZONS+10` childless roots.
- **Round 3 (fold into parent, mark the parent permanently
  non-evictable, walk `parent_prefix` repeatedly on lookup):** this fixed
  round 2's under-report, but `preserve_reclaimed_horizon`
  (`sqlite.rs:308-331` in the PR diff) evicts exactly one victim and then
  **unconditionally inserts its fold target with no cap re-check**. Every
  distinct childless root's fold target (one level up, per API group) is
  a *never-seen* key the first time it is reached, so that insert is a net
  `+1`, cancelling the victim's `-1` — net map size change 0, not −1. Worse,
  once a key becomes a fold target it is permanent
  (`ReclaimedHorizons::fold_targets`), so it can never later be evicted to
  recover that lost slot. Reproduced: churn 8192 keys against a cap of
  4096 → `horizons.len() == 8192`, cap never reached. The PR's own new test
  for this scenario asserted the childless-root *correctness* fix but never
  asserted the *boundedness* invariant its sibling test did — why CI missed
  it.

**Common thread:** the fold destination in all three is *another map key*,
and the space of possible fold-destination keys (parent prefixes, and —
after round 2's bug — grandparent/group prefixes) is not itself bounded by
anything smaller than the space of prefixes being evicted in the first
place (CRD groups churn too, over a long process lifetime). Folding into a
key can never be made safe-and-bounded simultaneously without also
capping *that* tier, and every attempt to cap a tier reintroduces the same
problem one level up. This is a well-known conflict but the PR's design
doc claims ("bounded... see that field's doc") never actually confronted
it — hence "3rd needs-changes, redesign not another patch" in the bead's
own notes.

## 3. Proposed design: fold into an atomic, not a key

Replace `reclaimed_horizons: HashMap<String, u64>` with a bounded map (cap
`N`, e.g. keep the existing `MAX_RECLAIMED_HORIZONS = 4096`) plus **one**
`AtomicU64` overflow floor, process-wide:

```rust
struct ReclaimedHorizons {
    entries: HashMap<String, u64>,      // capped at MAX_RECLAIMED_HORIZONS
    overflow: AtomicU64,                // fetch_max-only, never decreases
}
```

- **Insert** (`preserve_reclaimed_horizon`): insert the new entry; if
  `entries.len() > N`, pick a victim (min-by-horizon is a fine heuristic —
  revisions only increase, so the lowest floor is both the value least
  likely to matter to any live watch and needs no extra ordering
  structure), `entries.remove(victim)`, then `overflow.fetch_max(victim's
  horizon, Relaxed)`. The fold destination is an atomic, not a map slot —
  there is no key to be novel, so this is **structurally** a net `-1` on
  every over-cap insert, with no cap re-check ever required. This is the
  exact class of bug round 3 hit, closed by construction rather than by a
  second check.
- **Lookup** (`find_reclaimed_horizon`): exact match on `prefix` → else
  exact match on `parent_prefix(prefix)` (the one-level-up
  resource-type-root string; the codebase's own docs at `sqlite.rs:898-903`
  establish a watch prefix is always exactly a shard root *or* that root
  plus one namespace segment, never deeper, so one parent hop is
  provably sufficient — no `while`-loop, no dependence on how many times
  something has been folded) → else `overflow.load(Relaxed)`. Three O(1)
  steps, worst case, regardless of how many prefixes have ever been
  abandoned over the process's life. No linear scan.
- **`get_or_create_shard`'s reseed-on-recreate** must also fall back to
  `overflow.load()` instead of `unwrap_or(0)` when the exact entry is
  gone — otherwise a shard recreated after its exact entry aged out of the
  cap would wrongly seed `horizon = 0`.

**Bound:** exactly `N + 1` words of state, fixed, independent of
namespace or CRD-group churn — the leak class in `mayor-17nj7.4`'s
original description is closed by construction.

**Lookup complexity:** O(1) (two hashmap probes + one atomic load) vs. the
current O(n) `.iter().filter(starts_with).max_by_key()` scan run on every
watch-open (`watch.rs:803`).

**Failure modes this closes, mapped to the three attempts:**
- Round 1's under-report (discard-on-evict): closed — every eviction still
  lands somewhere queryable (the atomic), never just dropped.
- Round 2's childless-root under-report: closed — lookup fallback is
  *unconditional* (atomic is always the last resort for every prefix
  shape), not dependent on a fold chain landing at a depth the lookup
  happens to check. There is no "one level too shallow" failure mode left
  because there is no second key hierarchy to misjudge the depth of.
- Round 3's unbounded growth: closed by construction — the fold target is
  never a `HashMap` key, so "was this insert's key novel" cannot affect
  the map's size change on eviction; it is always exactly −1.

**Cost of the trade:** entries older than the cap lose per-type precision
and share one coarse global floor instead — the same "conservative in one
direction only" trade the codebase already accepts for
`SqliteStore::compaction_horizon()` (`sqlite.rs:451-460`, its own doc:
"a busy shard can occasionally make a quiet shard's watch look expired a
little earlier than strictly necessary... never the reverse"). This is
matching, not inventing, an existing convention (Rule 11).

## 4. Verdict on mayor-17nj7.4 / PR #1556

**PR #1556 is superseded by this redesign, not fixable by a fourth patch
on its own structure.** All three of its attempts share the fold-into-a-key
root cause in §2; a fourth attempt patching that same shape (e.g. "also cap
the group-level tier") would just push the unbounded-growth failure mode up
one more level, as round 2 → round 3 already did once. The branch
(`worker/agent-a2f40b04fb9d1c092`, origin) contains useful regression
tests (`sqlite.rs:5920` and `5992` in the diff) worth salvaging for the new
design's own test suite — they already exercise both the namespace-churn
and childless-root scenarios end-to-end through `watch()`, they just need
their assertions retargeted at the new `entries`/`overflow` shape. Do not
merge PR #1556 as-is; close it in favor of the follow-on bead below.
