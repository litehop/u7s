# eBPF ServiceLB memory-monitoring design

Bead: mayor-aie31.6
Date: 2026-09-04
Status: design (Shape 3) — implementation is the follow-on bead this doc files

## Answer

Build one dedicated, standalone script, `scripts/servicelb/sample-ebpf-memory.sh`,
that reads `bytes_memlock` (bpftool's `memlock` text field) off every map the
three servicelb tc-bpf programs reference — discovered via `bpftool prog show
pinned <pin-dir>/<prog>-prog --json`'s `map_ids` field, never the unfiltered
global `bpftool map show` (which also lists unrelated kernel/host maps) — plus
loader RSS via `ps`/`pgrep`. It has two modes: `once` (a single snapshot pair
of CSV rows) and `start`/`stop` (a background interval loop, same idiom as
`scripts/conformance/sample-run-metrics.sh`). `once` wires into the Tier-1
smoke gate (`scripts/servicelb/smoke-remote.sh`) and a new CI job promoted
from today's throwaway spike; `start`/`stop` is the tool Phase-4 gate-2
(mayor-lrbvo) needs for a real-node soak measurement. This is a NEW script,
not an extension of `sample-run-metrics.sh` — see "Decision 3" for why.

Verified live on `lima-node-smoke` (see "Evidence" below): the field is
`memlock` in bpftool's text output, `bytes_memlock` in `--json`, reported per
map id in bytes.

## Evidence: bpftool field, verified live

Built `u7s-servicelb` + `servicelb-ebpf` from this worktree's HEAD (nightly +
bpf-linker + cargo-zigbuild, `aarch64-unknown-linux-gnu`), copied to the free
`lima-node-smoke` VM, and ran `scripts/servicelb/smoke-remote.sh run` — the
real Tier-1 fixture (veth/netns, Geneve, one full client→VIP→backend round
trip). `VERIFIER-ACCEPT: PASS` / `ROUND-TRIP: PASS`. `sudo bpftool map show`
against the live maps:

```
189: hash  name VIP_MAP       key 8B  value 8B  max_entries 16  memlock 2752B
190: array name CONFIG        key 4B  value 8B  max_entries 1   memlock 312B
191: hash  name REV_FLOW      key 16B value 12B max_entries 64  memlock 7744B
192: hash  name POD_TARGETS   key 4B  value 2B  max_entries 32  memlock 4032B
193: hash  name FWD_FLOW      key 16B value 4B  max_entries 64  memlock 7168B
```

Total: **22,008 bytes (~21.5 KiB)** across all 5 servicelb maps at today's
Phase-2/3 fixture scale (16/32/64 entries) — two to three orders of magnitude
below `ebpf-toolchain-aya.md`'s informal 4–7 MiB/map estimate. That estimate
was written for a `PERCPU_HASH` design; the current maps on `main` are plain
`BPF_MAP_TYPE_HASH` (bd memory `servicelb-lru-percpu-hash-breaks-conntrack`
already ruled out `LRU_PERCPU_HASH` for correctness — cross-CPU packets of one
flow broke conntrack reads) and pa0ze's still-in-flight branch is expected to
move them to `LRU_HASH` (shared single table, still not per-CPU). This is the
concrete confirmation of the bead's "measure, don't estimate" note: the real
number is tiny today, and neither `HASH` nor `LRU_HASH` change that order of
magnitude — the doc's static per-CPU estimate was simply the wrong map type.

`bpftool prog show pinned <pin-dir>/uplink_ingress-prog --json` returns
`"map_ids":[189,193,190]`; unioning across all three pinned progs
(`uplink_ingress`, `geneve_ingress`, `uplink_egress_return`) gives exactly
`{189,190,191,192,193}` — the 5 servicelb maps and nothing else. This is the
identification method: walk the pinned progs, not the global map list.

Nit for whoever next touches `crates/servicelb/README.md` (not fixed here —
out of scope, and pa0ze owns that crate on another branch right now): its
"Memory observability" section shows `bpftool prog show pinned
.../uplink_ingress.prog` (a dot); the loader (`src/main.rs`'s
`attach_and_pin`) actually pins `<pin-dir>/<name>-prog` (a hyphen) — verified
against the live pin directory (`ls /sys/fs/bpf/servicelb-smoke` showed
`uplink_ingress-prog`, not `.prog`).

## Decisions + rationale

**1. Continuous vs point-in-time — both, split by where a trend is
observable.** The Tier-1 smoke fixture's live window between "all 3 hooks
attached" and cleanup is under 2 seconds (measured: the CI spike's whole
load→verify→attach→round-trip sequence completed in the same job-log second).
Polling on an interval inside that window cannot show a trend — one snapshot
right after attach is the actual ceiling of what's observable there, and is
already strictly better than today's nothing. A real trend only exists where
the loader runs for minutes-to-hours: Phase-4 gate-2's real-node soak
(mayor-lrbvo, still open) and any future longer-lived local run. So: `once`
mode for the short-lived harness/CI gate, `start`/`stop` interval-loop mode
(reusing the exact pidfile/background-loop idiom already proven in
`sample-run-metrics.sh`) for gate-2's real-node measurement. This satisfies
the operator's "not a one-shot" requirement at the point where a trend can
actually exist, without pretending a 2-second fixture has one.

**2. Output format: CSV, two files, matching `rss.csv`/`vm-free.csv`.** Two
files rather than one ragged schema: `ebpf-map-memory.csv`
(`ts,map_id,map_name,map_type,max_entries,bytes_memlock`, one row per map per
tick — 5 rows/tick today) and `loader-rss.csv` (`ts,pid,rss_kb`, one row per
tick). This is a fixed-shape, small, tabular time series — CSV is the
established convention (`sample-run-metrics.sh`'s three CSVs) and needs no
new tooling to grep/diff in a CI log or `limactl copy`'d back to a host.

**3. Integration point: a dedicated `scripts/servicelb/` script, NOT an
extension of `sample-run-metrics.sh` — the bead's own premise for that half
doesn't hold today.** `sample-run-metrics.sh` samples `apiserver`/
`scheduler`/`konnectivity-server` and top-N VM processes for a `run-all.sh`
conformance session; it assumes the process it wants to add is colocated in
that VM/session. `u7s-servicelb` never is: today it only runs inside the
Tier-1 smoke fixture's own disjoint VM (`lima-node-5`/`lima-node-smoke`,
separate from any `run-all.sh` VM, no apiserver/kubelet/KCM involved at all),
and per `mayor-aie31`'s epic notes, Phase-4 gate-2 also deploys it via the
standalone Phase-1 manual loader against a real node — explicitly NOT the
Phase-5 DaemonSet, which is the only future state where it WOULD run
colocated with a `run-all.sh` conformance session, and Phase 5
(`mayor-9gr0n`) is still open. Wiring `sample-run-metrics.sh` today would
either be dead code (nothing to `pgrep` for) or wire against the wrong
process model. The dedicated script needs zero dependency on the
conformance stack's VM/workdir/kubeconfig conventions — only a pin-dir and an
optional loader binary name — so it works unmodified against the smoke
fixture, a bare CI runner, and a real fleet node alike. Revisit folding it
into `sample-run-metrics.sh`'s `resolve_*_pid` pattern once Phase 5 actually
puts the loader inside a `run-all.sh` session — not before.

**4. CI: yes, promote the spike — it's proven and it's cheap.** A throwaway
`zz-ebpf-ci-spike` workflow (run 33882862825, 2026-09-04T14:17:27Z–14:18:37Z,
**70 seconds** total job time) proved the full Tier-1 harness — load, verifier
accept, attach, one real round trip — runs natively on a plain `ubuntu-latest`
runner: no Lima, no cross-compile (the runner is amd64, so it's a normal
native `cargo build --release`), `bpftool` fetched as a hash-verified prebuilt
binary from `libbpf/bpftool`'s GitHub release (same trust pattern
`taiki-e/install-action` already uses for `bpf-linker` in the existing
`ebpf-build` job) — `PHASE:LOAD=PASS / PHASE:VERIFY=PASS / PHASE:ATTACH=PASS /
PHASE:ROUNDTRIP=PASS`. Given that, adding one `once`-mode memory snapshot
right after the round-trip assertion (before the existing cleanup step) is
near-free on top of a job that already exists in spike form. Recommend a
loose regression ceiling, not a tight one: total `bytes_memlock` across the
5 servicelb maps must stay under 1 MiB (measured today: ~21.5 KiB, ~45x
headroom) — catches a gross accidental `max_entries` blow-up without being
flaky against pa0ze's in-flight `LRU_HASH` resize, whose real numbers this
design deliberately doesn't try to predict.

**5. Phase-4 gate-2 (mayor-lrbvo): this script IS the tooling gate-2's own
description asks for.** Gate 3 of that bead reads "userspace RSS and kernel
eBPF-map memory both independently and continuously monitorable in practice
... using the tooling Phase 1 landed — not merely assumed stable from a
point-in-time check." `start`/`stop` mode against a real node's pin-dir and
loader PID is exactly that tooling; gate-2 owns getting it onto real
Linode/Scaleway/home-NAT hardware, not rebuilding it.

## What this design does not cover

- Does not change any servicelb-ebpf map type, size, or eviction policy —
  measurement only, per the "do not modify servicelb source" constraint.
- Does not fix `crates/servicelb/README.md`'s `.prog`/`-prog` nit (flagged
  above; leave for whoever next touches that crate).
- Does not pick the CI regression ceiling's exact final value beyond the
  1 MiB starting point above — the follow-on bead can tighten it once
  pa0ze's `LRU_HASH` change lands and real conntrack-scale numbers exist.
