# CSI attached-volume tally: is sync resolution via NodeTally feasible?

Bead: mayor-6dj51.5

## Verdict

**Neither pure (A) nor pure (B).** The bead's blocker ("requires async I/O
NodeTally's synchronous apply_event/assume can't do today") is **true for
`apply_event`** but **false for `assume()`**: `assume()` already has
zero-I/O access to the pending pod's own resolved CSI driver counts
(`PendingPod::csi_volume_counts` — resolved by the caller *before*
`pick_node`/`assume()` ever run, same as `pvc_names`/`requests`/`host_ports`).
The scheduler holds **no PVC/PV/StorageClass informer** at all — only a Pod
watch — so `apply_event`, which must recompute every `TalliedPod` field from
nothing but the raw watch-event JSON, genuinely cannot resolve an arbitrary
bound pod's PVC → CSI-driver mapping without a live GET.

**Recommendation: a small "assumed CSI reservations" side-ledger in
NodeTally, overlaid on top of the existing live-GET scan** — not a full
NodeTally field mirroring `pvc_names`, and not a new informer buildout. This
closes the exact race in the bug report with a self-contained, small diff,
no new watch loops, and no blocking-mutex-across-await problem. Full
informer-backed replacement (PVC/PV/StorageClass watches feeding a
sync-readable cache) is the "proper" long-term fix but is materially more
invasive; not warranted for a P2 fix to a narrow, same-batch-creation race.

## Evidence

### 1. How NodeTally stays synchronous today (`crates/scheduler/src/lib.rs`)

`NodeTally::apply_event` (lib.rs:1488-1566) recomputes `TalliedPod`'s
`requests`, `host_ports`, `pvc_names` **entirely from the pod spec in the
watch event itself** — `pod_total_requests`, `container_host_ports`,
`referenced_pvc_names` (lib.rs:702) are pure functions over
`spec.containers`/`spec.volumes`, no I/O. `pvc_names` in particular is just
the *bare PVC name* string copied out of
`volumes[].persistentVolumeClaim.claimName` (lib.rs:1515-1521) — it never
needs to know what the PVC resolves to, only its name (used for RWOP
same-PVC conflict detection, a pure string-equality check).

`NodeTally::assume` (lib.rs:1590-1617) is called from
`select_and_reserve_node` (lib.rs:3030-3058) and
`verify_and_reserve_preemption` (~lib.rs:3405) **before the bind's HTTP call
completes**, under a `std::sync::Mutex<NodeTally>` (run.rs:869, `.lock()`
calls throughout run.rs — a *blocking* mutex, not `tokio::sync::Mutex`).
Both call sites pass in fields already computed on `PendingPod` by the
caller (`pod.requests.clone()`, `pod.host_ports.clone()`,
`pod.pvc_names.clone()` — lib.rs:3047-3056) — zero I/O happens inside the
locked critical section. This is *why* it's safe: a blocking std Mutex
cannot be held across an `.await` at all (doesn't compile under normal
Send-future rules), so anything `assume()`/`apply_event` do must already be
synchronous by construction, not just by convention.

The mayor-6dj51.2 RWOP pattern threading `pvc_names` through `assume()`
works precisely because `pvc_names` needs no resolution — it's intrinsic to
the pod's own spec, already known to the caller for free.

### 2. What `populate_csi_driver_headroom` does today (lib.rs:4225-4256)

Two live GETs per scheduling decision that needs a CSI volume:
- `fetch_csi_driver_limits_by_node` (lib.rs:4141) — `GET
  /apis/storage.k8s.io/v1/csinodes`, per-node per-driver `allocatable.count`.
- `fetch_attached_csi_volume_counts_by_node` (lib.rs:4182) — **one
  cluster-wide `GET /api/v1/pods`**, then for every non-terminal node-bound
  pod with PVCs, `count_csi_volumes_by_driver` → `resolve_csi_driver`
  (lib.rs:4023) does a `GET .../persistentvolumeclaims/{name}`, then
  (bound case) `GET .../persistentvolumes/{name}` for `spec.csi.driver`, or
  (unbound/fallback case) `GET .../storageclasses/{name}` for
  `spec.provisioner`.

This is the "used" (attached) side. The "want" side —
`PendingPod::csi_volume_counts`, the pending pod's *own* PVCs' driver
counts — is resolved once via `fetch_csi_volume_counts` (lib.rs:4083) in
`run.rs`'s `handle_pod_event` (run.rs:609-628), **before** the first
`pick_node` call (run.rs:662). By the time `select_and_reserve_node` runs
under the tally lock, `pod.csi_volume_counts` is already a plain, resolved
`BTreeMap<String, i64>` sitting on `PendingPod` — no different in kind from
`pod.pvc_names` at that point.

The race: `assume()` closes the read-after-write gap for cpu/mem/hostPorts/
pvc_names by recording pod1's reservation in-process the instant it's
decided, before pod1's bind PATCH lands in the apiserver. The CSI "used"
count has no such in-process record — it's *purely* re-derived from a live
`GET /api/v1/pods`, which can run before pod1's PATCH has committed, so
pod2's scan undercounts pod1's not-yet-committed attachment.

### 3. The crux — is PVC → CSI-driver sync-resolvable from an existing cache?

**No cache exists.** Grepped `crates/scheduler/src/*.rs` for
`watch_stream(` / `*_WATCH_PATH` calls (the only mechanism this scheduler
uses to build an in-memory, watch-maintained cache — see `NodeTally` itself,
and the doc comment at lib.rs:1454 explicitly contrasting it with "a real
kube-scheduler's informer cache"): the **only** result is `POD_WATCH_PATH`
(run.rs:442, `client.watch_stream` at lib.rs:123). There is no watch, no
informer, and no synchronously-readable cache for PersistentVolumeClaim,
PersistentVolume, or StorageClass anywhere in the scheduler crate — every
access to those three kinds (`fetch_pvc_binding_info`,
`fetch_pv_csi_driver`/`fetch_pv_node_affinity`,
`fetch_storage_class_provisioner`/`fetch_storage_class_binding_mode`,
lib.rs:3620-3812) is a fresh, on-demand `http_get`.

So: for a pod `apply_event` learns about **that this scheduler process did
not itself just `assume()`** (initial relist at startup/reconnect —
`NodeTally::clear()`, lib.rs:1648, wipes `pods` and rebuilds it from
`sendInitialEvents=true` ADDED events — or any other already-bound pod with
PVCs observed later on the normal watch stream), `apply_event` has **no way**
to resolve that pod's CSI driver identity without a live GET, and it cannot
do a live GET: it is not `async`, and even if it were, the surrounding
`std::sync::Mutex` guard cannot be held across an `.await`.

This also rules out simply adding `csi_volume_counts` as a plain field on
`TalliedPod` filled only by `assume()`: `apply_event`'s ADDED/MODIFIED branch
(lib.rs:1524-1538) **overwrites** the whole `TalliedPod` entry at the same
key `assume()` used, the moment the real bind's watch event round-trips —
which happens quickly. If that overwrite can't also produce a correct
`csi_volume_counts` (it can't, per above), the freshly-`assume()`d value
would be silently erased and replaced with empty/default the instant the
watch confirms the very bind that made it correct — permanently
undercounting that node/driver until the pod is deleted. That would trade
one race for a guaranteed-wrong steady state, which is worse.

### 4. Recommended fix shape: assumed-reservations overlay (not a NodeTally field)

Mirror `reserved_victims`/`waiters` — an existing example of a **side-ledger
in NodeTally that is not part of `TalliedPod`'s per-field-recomputed
model** — rather than mirroring `pvc_names`.

1. Add `assumed_csi_volumes: HashMap<String, (String /* node */,
   BTreeMap<String, i64> /* driver → count */)>` to `NodeTally`, keyed by
   `"namespace/pod_name"` (same key as `pods`).
2. `assume()` gains one more parameter, `csi_volume_counts:
   BTreeMap<String, i64>` — the caller passes `pod.csi_volume_counts.clone()`
   (zero new I/O: already resolved pre-lock, per §2). Skip the insert when
   empty, matching the "no PVCs → no extra work" convention
   `populate_csi_driver_headroom` already uses.
3. `apply_event`'s three branches that already retire a `pods` entry for a
   key (DELETED; real-node-bound overwrite; terminal-phase removal —
   lib.rs:1504-1548) also drop that key from `assumed_csi_volumes`: once the
   watch confirms the bind (or the pod is gone), a subsequent live GET is
   guaranteed at-least-as-fresh (same apiserver store), so the ledger's job
   for that pod is done. The "still unbound" branch (lib.rs:1549-1564) must
   **not** touch the ledger, for the identical reason it must not touch
   `pods` — the documented phantom nominatedNodeName-echo case.
4. `NodeTally::remove` (rollback on bind failure, lib.rs:1623) and `clear`
   (watch reconnect, lib.rs:1648) also drop/clear the new map — same
   lifecycle as `pods`.
5. `populate_csi_driver_headroom` (lib.rs:4231) adds a new
   `tally.lock()`-scoped step: fold `assumed_csi_volumes`' still-live entries
   into `attached_by_node` (per node, per driver, summed) **before**
   computing `csi_driver_headroom` — a pure in-memory merge, no new I/O.

This keeps `resolve_csi_driver` and the live cluster-wide pod scan exactly
as they are today (still the source of truth for every pod this process
didn't itself just bind) and adds only a small, bounded, self-cleaning
overlay for the narrow window between `assume()` and that pod's bind
becoming visible on the watch — exactly the window the bug report identifies.
Mechanical cost: every existing `assume()` call site (~20, mostly tests)
gains one trailing argument.

### Alternative considered and rejected: TTL-based ledger expiry

Instead of removing ledger entries on the matching `apply_event`/`remove`
call, expire them after a fixed duration (e.g. 30s). Rejected: it reopens a
window (too short races again; too long over-counts and can wrongly reject
a schedulable pod) for no simplification — the identity-based removal hooks
into match arms that already exist and already handle this exact pod-key
lifecycle for `pods` itself.

### Alternative considered and deferred: full PVC/PV/StorageClass informers

Add watch loops for PersistentVolumeClaim, PersistentVolume, and
StorageClass, maintaining synchronously-readable PVC→driver caches so
`apply_event` really can recompute `csi_volume_counts` for any bound pod
from nothing but its own state, matching the `pvc_names` model exactly. This
is the architecturally "cleanest" fix and the one that would generalize to
other future external-lookup predicates, but is 3 new watch streams plus
ordering/staleness handling (a pod's bind can watch-race ahead of its PVC's
resolution) for a P2 bug that only manifests when two pods needing the same
driver's last slot are created in the same batch. Not recommended now; worth
revisiting if another predicate needs the same PVC/PV/StorageClass identity
data (e.g. real topology-aware provisioning).
