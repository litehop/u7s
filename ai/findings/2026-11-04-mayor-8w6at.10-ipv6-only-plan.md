## 2. Upstream reference (1.37.1)

Primary sources, fetched with `gh api` into `temp/research/`:

- Dual-stack docs: `k8s-dual-stack.md` ("single-stack IPv6 networking" is a supported mode; flags: `--service-cluster-ip-range`, `--cluster-cidr`, `--node-cidr-mask-size-ipv4|ipv6`, kubelet `--node-ip`).
- KEP-563 (`kep-563-dual-stack.md:83-125`): IPv6-only clusters have been supported since 1.9; the dual-stack work keeps them backward compatible. Single-stack v6 `kubernetes.default` gets a v6 ClusterIP.
- e2e: `test/e2e/e2e.go:118-129` (`getDefaultClusterIPFamily`) sets `TestContext.IPFamily` from the `kubernetes` Service ClusterIP, so the whole conformance suite adapts to a v6 cluster with no flag. Service tests branch on `ClusterIsIPv6()` (`k8s-e2e-service.go:1313, 2372`, EndpointSlice `addressType = IPv6`). `test/e2e/network/networking.go:93` has `[Feature:Networking-IPv6][Experimental][LinuxOnly]` "should provide Internet connection for containers" (dials `2001:4860:4860::8888:53`).
- CI: upstream runs `pull-kubernetes-conformance-kind-ipv6-parallel` and `pull-kubernetes-e2e-kind-ipv6` (test-infra `config/jobs/kubernetes/sig-testing/conformance-e2e.yaml`, `config/testgrids/.../presubmits/config.yaml`; found by `gh search code`, job bodies not fetched).
- kube-proxy (`k8s-kubeproxy-server.go:259-278`): the proxier is dual-stack when the kernel supports both families, independent of node addresses; primary family comes from node IPs. `checkBadIPConfig` (`:320-350`) fails on `node.spec.podCIDRs` of the wrong family.
- Known kubelet/KCM caveats: KCM node-ipam allocates one CIDR per `--cluster-cidr` entry for every node (`k8s-nodeipam-range_allocator.go:84-95, 316-339`); the per-node mask must leave at most 16 host bits against the cluster prefix (a v6 `/64` mask needs a cluster CIDR no shorter than /48; verify against `validateMaxCIDRRange` before choosing D4's default). Not re-fetched: kubelet `address: 0.0.0.0` default (`k8s-kubelet-defaults.go:85-86`) relies on Go's dual-stack wildcard socket; unverified live.

GCE (docs fetched with curl from docs.cloud.google.com on 2026-11-04):

- Images: "IPv6-only instances support only Debian, Red Hat, and Ubuntu operating systems" and "don't support Compute Engine Internal DNS" (`gcp-ipv6-support.txt:3904-3905`). u7s targets Ubuntu, so the OS is fine; anything that resolves `*.internal` (including `metadata.google.internal`) is a risk.
- Subnet stack type is immutable both ways for IPv6-only: "you can't change a dual-stack or IPv4-only subnet to IPv6-only. Conversely, you can't change an IPv6-only subnet to IPv4-only or dual-stack" (`gcp-subnets.txt:4210-4211`). The access type (internal/external) is also immutable. The existing `u7s-test` subnets (`scripts/gcp/setup.sh:62-90`, `IPV4_IPV6`/`EXTERNAL`) cannot be converted; a new subnet is needed, which can live in the same VPC.
- Create: `gcloud compute networks subnets create SUBNET --network=N --stack-type=IPV6_ONLY --ipv6-access-type=EXTERNAL --region=R`; instance `--network-interface=network=N,subnet=S,stack-type=IPV6_ONLY` (`gcp-connect-ipv6-to-ipv4.txt:3485-3560`).
- IPv4 destinations only through DNS64 plus NAT64: Cloud DNS policy `gcloud dns policies create NAME --networks=N --enable-dns64-all-queries` (synthesises `64:ff9b::/96`), and Cloud NAT `gcloud compute routers nats create NAT --router=R --region=REG --auto-allocate-nat-external-ips --nat64-all-v6-subnet-ip-ranges` (`gcp-connect-ipv6-to-ipv4.txt:3680-3880`). NAT64 supports second-generation or earlier VMs and M3 (`gcp-ipv6-support.txt:3925`); the harness's e2-standard-2 qualifies. Cloud DNS does not support IPv6 inbound forwarding (`:3921`).
- IAP: firewall must allow `2600:2d00:1:7::/64` for IPv6 VMs (`gcp-iap-tcp.txt:3354`). Whether `gcloud compute ssh --tunnel-through-iap` reaches an instance with no IPv4 NIC at all is not documented; unknown without a live test (the dual-stack run only proved IAP over the VM's IPv4, `dual-stack-state.md:57-59`). Fallback: SSH over the VM's external v6 address from a v6-capable host, or a dual-stack bastion in the same VPC.

## 4. Mixed-stack cluster (some nodes dual-stack, some IPv6-only)

**Verdict: unsupported in practice. Upstream neither forbids nor tests it, but every layer that carries IPv4 pod traffic across nodes assumes IPv4 on every node. Recommend not pursuing; this is operator decision D5, not a bead.**

(1) Upstream stance. No doc or KEP forbids it. KEP-563 and the docs assume each node is provisioned for the cluster's families: the docs list "Provider support for dual-stack networking (...must be able to provide Kubernetes nodes with routable IPv4/IPv6 network interfaces)" (`k8s-dual-stack.md:49-51`), and the KEP's operator checklist says "ensure that nodes (where the pod is running) are configured for dual-stack... CNI... kubelet..." (`kep-563-dual-stack.md:1583-1595`). Mechanically: node-ipam allocates a podCIDR for every cluster CIDR to every node regardless of its addresses (`k8s-nodeipam-range_allocator.go:84-95, 316-339`), so a v6-only node gets a v4 podCIDR it cannot route; kubelet accepts a single-family `--node-ip`; hostNetwork pods follow the node's own addresses (KEP checklist item 5), so on that node they are v6-only and never appear in v4 EndpointSlices; Node `status.addresses` carries only v6.

(2) What breaks on such a node:
- flannel: the family set is cluster-wide net-conf (`flannel-main.go:282`, `GetIPFamily(config.EnableIPv4, config.EnableIPv6)`) and the interface lookup is done for that stack; a node without a v4 address cannot satisfy a dual-stack config (exact failure message not captured; needs a live test). vxlan keeps a device per family (`flannel-vxlan.go:202-232`), so v4 pod traffic has no v4 underlay to ride.
- kube-proxy: installs v4 and v6 rules (dual-stack is decided by kernel support, `k8s-kubeproxy-server.go:264`), so v4 Service VIPs resolve but DNAT to v4 pod IPs that are unreachable cross-node. `default/kubernetes` is single-stack on the primary family (`lib.rs:2790-2796`): in a v4-primary cluster its endpoint is a v4 apiserver address a v6-only node cannot reach, so in-pod clients (`KUBERNETES_SERVICE_HOST`) fail.
- CoreDNS/Endpoints: v4 Service endpoints on that node's pods (v4 podIP from the allocated podCIDR) are only reachable intra-node; a pod there cannot reach a v4-only Service backend elsewhere.
- beep: per-backend Geneve tunnel remote can be v4 or v6 (`beep-ebpf-main.rs:650-660`), so a v4 LB leg to a v6-only backend node could in theory traverse a v6 tunnel, but the inner backend is a v4 pod IP on a node with no v4 pod routing, and the v6 arm is unconfirmed. Unverified.
- node-to-node: v4 traffic has no path unless NAT64/CLAT is added, which only exists for internet destinations on GCE.

(3) u7s today refuses it: `reconcile_node_ips_with_families` (`install.sh:828-871`) errors when the node lacks a cluster family ("the cluster uses IPv4 ... node addresses have no IPv4 address"); a joining worker learns the cluster families from `kube-system/u7s-cluster-config` (`install.sh:1161-1181`; published by `crates/apiserver/src/lib.rs:2865-2891`) before choosing `--node-ip` (`install.sh:1873`, `1919-1926`). A v6-only node joining a dual-stack cluster stops with that error before anything is touched. This was deliberate (#2078: "Missing required family is an error"). The apiserver does not itself validate Node addresses against families; the guard is the installer only.

(4) If the operator wants it, it would be its own research bead after the IPv6-only gate (per-node EnableIPv4, kube-proxy family restriction, dual-stack Endpoints filtering), gated on a live spike; I did not file one.

## 6. Operator decision points (no beads filed)

- D1. Registry reachability on GCE: require DNS64/NAT64, or keep the images IPv6-native? ghcr.io has no AAAA (flannel). Options: NAT64 on the harness (cheap, but beep roadmap may forbid assuming it, D2), mirror the flannel images behind an IPv6-reachable host (like the tarball mirror), or switch to a docker.io-hosted flannel image if one is published (not verified here).
- D2. Confirm or retire the "beep must not assume NAT64/DNS64" constraint: the cited `roadmap.md:116` does not say it; if it is real it belongs in the roadmap or beep's decisions.
- D3. Is the Lima rig (host keeps v4, node addresses v6-only) an acceptable proof of install-time behaviour, or must the first full proof be on GCP v6-only (no host IPv4)?
- D4. Default v6 ranges when the node has no IPv4 (for example pod `fd00:10:244::/56` with `/64` per node, Service `fd00:10:96::/112`) versus requiring explicit flags.
- D5. Mixed-stack clusters (section 4): keep refusing (recommended).
- D6. Install-time internet dependency: the node needs apt, CRI-O keys, images; is NAT64 acceptable as the v6-only egress path for those, or must the install be fully IPv6-native?
