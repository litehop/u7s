## Which option rejects what

None of A, B, C rejects any measured real CRD. Headroom: B per-pattern
3.2x, C per-pattern 13x, A aggregate 94x, B count (non-trivial) 25x.
Real-user-CRD cost of A, B and C is therefore zero today; pick on bound
quality:

- C alone: unbounded in pattern count. 1.5 MiB / ~50 B per
  `"fN":{"type":"string","pattern":"..."}` entry is ~30k fields, each
  allowed up to 1 MiB compiled (so tens of GiB) per version.
- B: worst case 256 x 256 KiB = 64 MiB compiled, but the "non-trivial" cutoff
  needs a definition and trivial patterns remain uncounted (each is still
  <= 4 KiB so 30k x 4 KiB = 120 MiB; bounded but arbitrary).
- A: worst case = 32 MiB compiled + 1 MiB (resident ~1.5x, from #2289's
  15 MiB resident / 10 MiB NFA measurement), counts every pattern, one
  integer, no "trivial" definition. Real maximum sum is 357 KB, so 8 MiB
  would also pass with 23x headroom; 32 MiB leaves room for generated CRDs.

## Q4. Is the pathological case reachable upstream?

Measured here: `\pL{244}` compiles to 10,456,576 B in Rust `regex`
(`\pL{100}` = 4,284,864 B): the Unicode class is expanded into a UTF-8
automaton and **repetition copies it**, hence ~42 KiB per repeat count.
`[a-z]{1000}` is 72,208 B. 200 x `\pL{244}` is 1.4 KiB of schema, far inside
etcd's 1.5 MiB.

Go (verified in `src/regexp/syntax/parse.go`, go1.25.0): `maxSize` =
128 MiB / 40 B per Inst (~3.3M insts) per pattern; `maxRunes` = 128 MiB / 4;
repeat count <= 1000; and the source comment says "repetitions do not make
copies of the rune slices, so `\pL{1000}` is only one rune slice, not 1000"
(`\pL` = 1292 runes). So a Go `\pL{244}` is roughly 244 Insts x 40 B plus one
~5 KiB rune slice, i.e. ~15 KiB, about 700x smaller than Rust's. (Arithmetic
from the cited constants; I did not run Go.) Upstream is therefore exposed
in kind but not magnitude: 1.5 MiB / ~50 B per field = ~30k fields x
~15 KiB = ~450 MB (unmeasured estimate), against u7s's 30k x 10 MiB =
~300 GB for the same bytes. Upstream has no per-CRD total cap and nothing
besides etcd size (and Go's 128 MiB per-pattern) limits it; the real
upstream risk is lower by two to three orders of magnitude, which is why
u7s needs its own budget while upstream does not appear to have one.
Whether kube-apiserver compiles a CRD's patterns eagerly (validation) or
lazily (first CR) per field was not checked.

## Recommendation

1. Adopt A: 32 MiB summed compiled size per CRD (all versions, since each
   version is compiled for CR writes) plus the 1 MiB per-pattern cap already in
   #2289. Real CRDs use at most 1.1% of it.
2. Report the bound in the error message (field path + running total) so a
   rejected user can find the offender.
3. Do not add B's count limit.

Proposed follow-on beads (not filed):
- Raise or replace `MAX_CRD_PATTERN_BYTES` (1024): real Cilium CRD has a
  1199-byte pattern; fix the "113 bytes" comment; the O(n^2) ECMA rewrite
  concern needs a measured cost at e.g. 4-8 KiB before choosing the number.
- Verify the `ascii_shorthands` approximation against boon's exact ECMA
  output for the 81 measured CRDs (budget vs. what boon really compiles).
- Optional: fetch KubeVirt, remaining Cilium/prometheus-operator CRDs and a
  Crossplane provider with `pattern`-heavy schemas (upjet-aws biggest three
  have none).
