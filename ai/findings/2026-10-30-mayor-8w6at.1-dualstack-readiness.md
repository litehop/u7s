# Dual-stack / IPv6-only readiness inventory (u7s + beep + GCP)

Bead: mayor-8w6at.1 (epic mayor-8w6at). Date: 2026-10-30. Upstream target: Kubernetes 1.37.1 (release-1.37).

**Answer:** a GCP dual-stack verification is blocked today by eight gaps, and the
two "already landed" prerequisites are weaker than the epic assumes: mayor-7tqnq
only made the apiserver *reject* dual-stack Services (no IPv6 allocation exists),
and mayor-dqd2y only added dual node IPs to the Lima *conformance* harness
(`scripts/conformance/lima-start.sh`), not to `scripts/install.sh`. The whole
install path (install.sh, apiserver, manifests) is IPv4-only; beep is the
furthest along.

## Blockers, in dependency order

1. GCP test network is IPv4-only (`stack_type IPV4_ONLY`, read-only `gcloud` check) and
   `scripts/gcp/*` never request IPv6 (subnet, instance, firewall).
2. apiserver has one IPv4-only Service CIDR and allocator: no IPv6 ClusterIP, no
   `ipFamilies`/`clusterIPs` second family, `RequireDualStack` is rejected.
3. apiserver IPv6 papercuts that bite as soon as a v6 address exists: no `::1` SAN,
   `kubernetes` EndpointSlice hardcoded `IPv4`, IPv4-only CSR service-CIDR guard,
   pod-proxy podCIDR check and unbracketed `host:port` formatting.
4. install.sh cannot express a dual-stack cluster: IPv4-only CIDR parser, single
   `--cluster-cidr`/`--service-cidr`, KCM gets `--node-cidr-mask-size` (upstream KCM
   refuses it on dual-stack).
5. install.sh picks one IPv4 `IFACE_IP` (mayor-rv1aw, existing, open): kubelet
   `--node-ip`, apiserver `--listen`/`--advertise-address`, kube-proxy server URL.
6. Manifests carry no IPv6: flannel `net-conf.json`, kube-proxy `clusterCIDR`,
   CoreDNS Service families, beep `--pod-cidr`.
7. beep `--pod-cidr` accepts exactly one CIDR (one family), so on a dual-stack cluster
   every non-hostNetwork backend Pod of the second family is rejected (beep-side change).
8. No GCP harness path runs a dual-stack install plus the upstream
   `[Feature:IPv6DualStack]` specs (`scripts/e2e-install/cloud-two-node.sh` is IPv4).

## beep verdict

**beep is plausibly dual-stack capable (inner and, per its changelog, v6 underlay), but its own roadmap says "implemented, not validated on a real fleet", and one u7s-relevant limit exists.** Evidence from `litehop/beep` at `8f788a14` (2026-10-28; latest release v0.6.0, the version `manifests/beep.yaml` vendors):

- eBPF data path is dual-stack: `ebpf/src/main.rs:100-101` `ETH_P_IPV4`/`ETH_P_IPV6`, `:128-136` IPv6 header offsets and `TCP_CSUM_V6`/`UDP_CSUM_V6`, module doc `:9-18` (every v4 helper has a `_v6` sibling; keys are IPv6-primary with v4 stored `ipv4_mapped_v6`), Geneve tunnel key v6 arm `:632-660` (`remote_ipv6`, `BPF_F_TUNINFO_IPV6`), `:706` family-aware tunnel-key read.
- Controller honours `spec.ipFamilies`, dual-stack LB ingress, per-family front/underlay address selection from Node `status.addresses` (`CHANGELOG.md:296-300`, `controller/src/watch.rs:370-386`: front = ExternalIP else InternalIP, underlay = InternalIP else ExternalIP).
- v6 underlay: CHANGELOG 0.3.0 listed it incomplete (`CHANGELOG.md:426`), 0.4-0.6 added a family-aware tunnel-key read (#140) and an IPv6-only-node smoke (`scripts/smoke-k3s-controller-v6only.sh`); the code comment at `ebpf/src/main.rs:642-646` still says the v6 arm has no rig "to confirm it against" (comment may be stale; unverified).
- VIP announcement: none. Front IP is the node's own address, "no floating IP, no ARP/BGP announcement" (`docs/design/ebpf-lb-dataplane.md:49-50`), so no NDP work and no L2 dependency on GCP.
- Gap: `controller/src/main.rs:100` `--pod-cidr` is a single `IpCidr` (one family); `controller/src/reconcile.rs:139` admits a v6 pod IP only inside that CIDR or by the hostNetwork signature. beep's dual-stack smoke deliberately uses a hostNetwork backend (`scripts/smoke-k3s-controller-dualstack.sh:8-19`), so a real second-family pod backend is untested and would be rejected. `--node-ip` is also single (`status.hostIP`, `deploy/base/daemonset.yaml:121-155`), the primary family only.
- Tested on Lima/k3s only (`ai/extended-context/roadmap.md:26-33`); IPv6-native registry pull unverified (`roadmap.md:74`); `docker.io` is the image registry.

Inference (unverified): on GCE the external IPv4 is 1:1 NAT'd to the private address, so packets reach the VM with the private destination and beep's InternalIP front (v4) matches without a Node ExternalIP; the v6 external /96 is configured on the NIC (`/96`, first `/128` on the interface, DHCPv6; docs below), so the v6 front is the NIC address. Hence rv1aw's `--external-iface` should not be needed for GCP verification, only dual-address `--node-ip`. Confirm on a real VM.

## GCP feasibility (docs fetched into `temp/research/gcp-*.txt`; read-only gcloud used)

- Dual-stack subnets exist in all regions; `--stack-type=IPV4_IPV6 --ipv6-access-type=EXTERNAL` on subnet; VM `--stack-type=IPV4_IPV6` (docs.cloud.google.com `.../vpc/docs/subnets`, `.../compute/docs/instances/create-ipv6-instance`).
- The existing IPv4-only subnet can be converted to dual-stack (docs only forbid IPv4-only/dual to IPv6-only conversion and changing access type); `u7s-test` subnet is IPV4_ONLY today. Mutation needs operator approval (not done here).
- Each dual-stack/IPv6-only NIC gets a single /96; first /128 is configured on the interface via DHCPv6 plus RA default route.
- The implied IPv6 ingress deny rule needs explicit allow rules; IPv4 rules do not cover IPv6 (separate rules, `::/0` source for the LB test, plus intra-subnet GUA range for node-to-node and ICMPv6).
- e2-micro: no machine-type restriction on the dual-stack pages (unverified live; I could not create a VM). Spot is not mentioned as a restriction. The 1 GB shared core budget is the practical risk (`ai/findings` release-gate CPU/IO saturation note, commit `ff9de6da`).
- IPv6-only instances: supported on Debian, Red Hat and Ubuntu images only; the stack type of an IPv6-only instance cannot be changed; IPv6-only subnets can't be converted from dual-stack; reaching IPv4 destinations requires separately configured DNS64/NAT64 (page nav "Configure IPv6-only subnets and instances with DNS64 and NAT64"). `docker.io` and github.com releases are IPv4-reachable only (unverified, not checked), and IAP SSH on IPv6-only VMs unverified, so IPv6-only is a later phase.
- Not verified: whether `ubuntu-2604-lts-amd64` configures DHCPv6 out of the box.
