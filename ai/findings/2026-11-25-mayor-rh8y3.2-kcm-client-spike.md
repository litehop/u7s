# KCM client-stack spike: option C (existing hyper client + narrow informer) wins under D2

Option C holds 10k pods plus their ReplicaSets in 33.8 MiB idle `Pss_Anon`, 4% below the kube-rs runtime with narrow types (B) and 15x below kube-rs with full types (A), and pulls zero new crates versus 50 for A and B; N = 4416 bytes/pod.

## Numbers

Medians of 3 interleaved runs each. Apiserver seeded with 10011 pods (10000 bound to a fake node, 11 system) and 1003 ReplicaSets. `Pss_Anon` is the whole process after list and watch sync plus a 20 s settle. Bytes per pod is the `Pss_Anon` delta from a baseline taken after the client was built and before the first list, divided by pod count (ReplicaSets included). Live bytes come from a counting global allocator.

| Option | Idle Pss_Anon | Bytes/pod (Pss delta) | Bytes/pod (live heap) | New crates vs product lockfile | Watch events after sync |
|---|---|---|---|---|---|
| A: kube + kube-runtime, full k8s-openapi types | 502.4 MiB (514420 KiB) | 52551 | 46375 | 50 | correct |
| A-trim: A plus `managedFields` cleared via `WatchStreamExt::modify` | 243.8 MiB (249652 KiB) | 25469 | 20924 | 50 | correct |
| B: kube-runtime reflector, narrow own types | 35.2 MiB (36052 KiB) | 3625 | 1838 | 50 | correct |
| C: politeia hyper client + own informer, narrow types | 33.8 MiB (34612 KiB) | 3508 | 1845 | 0 | correct |

Raw runs (Pss_Anon KiB): A 514868 / 514248 / 514420; A-trim 249932 / 248780 / 249652; B 33480 / 37172 / 36052; C 34612 / 34492 / 35564.

D2 rule: lowest idle anon wins; within 10%, fewer new crates. C is lowest outright; B is within 10% (4.2%), so C also wins on crates. A loses by an order of magnitude even after trimming managedFields.

Crate counts: unique `name@version` in `cargo tree -e normal,build --target all` per spike package: A 200, B 200, C 74 (product workspace: 353). New by crate name versus the product workspace: A 50 (kube, kube-client, kube-core, kube-runtime, k8s-openapi, futures, json-patch, jsonpath-rust, pest*, jiff*, serde-saphyr, derive_more, ...), B the same 50, C 0. Binary size (file-backed, not in the anon numbers): A 9.1 MB, B 7.3 MB, C 4.3 MB.

Watch correctness: after sync each client was driven through create (3 pods), label update (3 pods), force-delete (1 pod). All four saw 6 applies (3 adds, 3 label updates), 1 delete, `v=2` on the updated pods in the store, and the deleted pod absent. This was identical in all 3 runs of every option.

## N

B_chosen = 3508 (C, Pss delta). 1.25 x 3508 = 4385, rounded up to a multiple of 64 = **4416**, written to `scripts/conformance/kcm-pod-bytes.txt`. The provisional 1024 target in the design is not reachable by any option here: even the allocator-only live heap is 1845 bytes/pod (narrow struct with a label `BTreeMap`, owner refs and condition strings). Using live bytes instead would give N = 2368; Pss was chosen because the memory gate measures `Pss_Anon`.

## Method

- Spike source (throwaway, committed for reproducibility): a separate cargo workspace at `spikes/kcm-client/`, with its own `[workspace]` and a lockfile seeded from the product `Cargo.lock` so shared crates sit at product versions. It is outside the product workspace, adds no dependency to any product crate, and is not part of CI. A raw copy goes to the mayor checkout's `temp/e2e/` if still present.
- All three build the same two informers (Pod, ReplicaSet), paged list (limit 500) then watch with bookmarks, and keep the same narrow fields: metadata (name, namespace, uid, resourceVersion, labels, ownerReferences), pod `status.phase` and `status.conditions[].{type,status}`, ReplicaSet `spec.replicas`.
  - A: `reflector::store::<Pod>()` and `ReplicaSet` with the k8s-openapi types.
  - B: `reflector::store` over own structs implementing `kube::Resource`. `Resource::meta()` returns `&k8s_openapi ObjectMeta`, so B converts the narrow metadata into a mostly-empty `ObjectMeta`; that is the minimum kube-runtime allows.
  - C: `politeia::kubeconfig_client` (the scheduler's `HyperApiClient`), `request` for pages, `watch_stream` for events, a `HashMap<ns/name, Narrow>` store (about 120 lines). It relists when the watch ends; it does not resume from the last resourceVersion.
- Cross-built with `cargo zigbuild --release --target aarch64-unknown-linux-gnu.2.35` (glibc malloc, same as shipped tarballs), one package at a time so rustls crypto-provider features are not unified across spikes. All run with `tokio` `current_thread`.
- Run inside `lima-node-4` (Linux, `/proc/self/smaps_rollup`) against the host rig apiserver at `https://host.lima.internal:6446`; page cache dropped before each run; order interleaved (a, a-trim, b, c) x 3.
- Seed: 1000 ReplicaSets (10 replicas, 10 namespaces) and 10 pods each carrying a controller ownerRef, 2 containers, env, resources and an emptyDir volume, bound to a nonexistent node `bench-node` with an Exists toleration, status set to Running with 4 conditions via the status subresource. The apiserver returns `metadata.managedFields` on these pods (about 4.7 KB JSON per pod, mostly `fieldsV1`).
- Metrics are printed by each client at 20 s after sync; events are driven by the harness after the metrics line.

## Threats to validity

- Retained-size dominance: A's cost is mostly `managedFields` (about 25 KB/pod live, the difference between A and A-trim); clearing it halves A but leaves 20.9 KB/pod live that I did not decompose. A would need much deeper trimming to compete, which defeats its "least code" advantage.
- B and C differ by 4.2% while B's own three runs span 33.5-37.2 MiB; the ordering of B and C is within run noise (about 3 MiB per the state doc). The choice rests on crate count, not on the anon difference.
- C is not feature-equal: no resourceVersion resume (relist on every watch end), no 410 handling, no backoff, no shared-informer fan-out, no event queue, no resync. Adding them adds code and some memory; the stateful pieces are small relative to the 10k-pod store.
- C's watch events pass through `serde_json::Value` (politeia's `watch_stream` API) before narrowing; transient, but a typed stream would be cheaper.
- The watch probe checks only `evt-*` names, so lost or duplicate events and resume gaps are untested; hardening (mayor-rh8y3.4) covers that.
- Synthetic pods: all pods have identical shapes, labels and short strings; real labels (more keys, longer values) raise B and C bytes/pod, and string interning was not tried. Pod status was set once; no churn. Pods had 2 containers; narrow structs ignore spec, so spec size does not affect B and C.
- Controller manager was stopped on the VM (killed to stop the ReplicaSet controller creating its own pods and the GC reacting) for the whole measurement; apiserver, scheduler and kubelet ran. A live KCM would add watch churn. Idle-only; no steady-state event rate measured.
- Single VM (8 vCPU, 8 GiB), single apiserver build, one seed. Crate counts compare name versus the product lockfile; the spike lockfile bumped `smallvec` (1.15.1 to 1.16.6) so counts by `name@version` differ by one for C.
- Each package was built alone, so each got its own default rustls crypto provider and TLS stack; that fixed cost is in the absolute `Pss_Anon` (C's pre-list baseline was 0.3 MiB, A and B's 0.6 MiB) but mostly not in the bytes/pod delta.
- Pss delta includes ReplicaSet objects (1003) and transient list-page allocator retention; both inflate bytes/pod slightly versus a pods-only figure.

## Recommendation

Adopt C for the KCM Rust client: reuse `politeia`'s `HyperApiClient` and write a small typed informer. Pin N = 4416 bytes/pod in `scripts/conformance/kcm-pod-bytes.txt` (design target 1024 was provisional and unachievable with any of these structs; narrowing or interning labels is the lever if it matters). If the informer proves too costly to maintain, B is the fallback at +4% anon and +50 crates, not A. Before Phase 3, re-measure C with resourceVersion resume and real label cardinality.
