# Conformance bounds on graceful-degradation levers (Kubernetes 1.37)

Bead: mayor-lewl1.1 (epic mayor-lewl1). Date: 2026-11-05. Read-only audit, n/a code changes.

**Answer: no Conformance test constrains any degradation lever's value (reserved memory, eviction thresholds, image GC, swap, MemoryQoS, APF behaviour); the only real Conformance couplings are (a) the node must stay Ready and un-tainted while the suite runs, and (b) allocatable CPU/pods must be large enough to host the suite's pods, so every upstream mechanism can be made to fire earlier through kubelet config defaults that u7s may scale with node size.**

Sources are upstream `release-1.37` (tip `91c32c2b`), cached under `temp/research/` (not committed; refetch with `gh api -H "Accept: application/vnd.github.raw" "/repos/kubernetes/kubernetes/contents/<path>?ref=release-1.37"`). KEPs/docs are `master`. Cache filename in brackets.

## u7s today (kubelet config)

`scripts/install.sh` (~line 1013) writes a minimal `KubeletConfiguration`: crio endpoint, `failSwapOn: false`, resolvConf, staticPodPath, clusterDNS/Domain, serverTLSBootstrap, x509 auth, rotateCertificates. It sets none of: `enforceNodeAllocatable`, `systemReserved`, `kubeReserved`, `evictionHard/Soft`, `imageGC*`, `memorySwap`, `kernelMemcgNotification`, `memoryReservationPolicy`, `memoryThrottlingFactor`, `maxPods`, `cgroupDriver`. So u7s runs pure upstream defaults (below). No swap is provisioned (see `ai/findings/2026-10-16-mayor-i4bvb-phase2-memory-protection.md`). u7s control-plane units already carry `OOMScoreAdjust=-997` (apiserver, KCM). The u7s apiserver has its own minimal in-flight limiter returning 429 + `Retry-After: 1` (`crates/apiserver/src/inflight.rs`); it does not implement APF queuing.

## Does any Conformance spec break with smaller allocatable?

Checked in `test/conformance/testdata/conformance.yaml` (462 entries) and the e2e sources of the scheduling specs:

- **Scheduler, resource limits** (`SchedulerPredicates ... validates resource limits`, predicates.go L333-437): reads **CPU** allocatable per node, fills 70% of the remaining CPU, then requests 50% of the max node allocatable and expects Pending. It is relative to allocatable, so a smaller CPU/memory-reserved allocatable does not break it. It does require filler pods to schedule: `requestedCPU = 0.7 * (allocatable - used)`; with ~0 CPU left the filler is 0m and the test degenerates but still passes. Memory allocatable is not read.
- **Preemption specs** (preemption.go L63, L138, L225, L328, L488, L683-737): use the extended resources `scheduling.k8s.io/foo` / `example.com/fakecpu` injected via node status, independent of real allocatable.
- **LimitRange specs** (limit_range.go L67-197): create pods with 50-600Mi memory requests and 50-600 Gi ephemeral-storage, but only exercise admission (no wait-for-Running), so allocatable is irrelevant.
- **Taint/eviction specs** (conformance.yaml L2630-2641): NoExecute `tolerationSeconds`, KCM taint-manager behaviour.
- **Framework coupling (real)**: `GetReadySchedulableNodes` drops any node with a NoSchedule or NoExecute taint the test pod does not tolerate (`isNodeUntainted`, e2e_fw_node_resource.go L304-312, L368-404). A MemoryPressure/DiskPressure taint appearing *during* a run turns the cluster into "no schedulable nodes" and fails specs. Therefore pressure thresholds must not trip under ordinary Conformance load on the target node size; scaling thresholds up on 1 GiB nodes is only safe if the idle + suite working set stays above the threshold.
- Not exhaustively verified: every Conformance spec's pod memory demand (462 specs; only the scheduling specs were read). Pod count assumptions: none found in the specs read; `maxPods` 110 default is untouched.

## Can defaults scale with node size?

Yes mechanically: every lever above is a `KubeletConfiguration` field that `install.sh` writes once at install, so it can compute values from `/proc/meminfo` (e.g. percentage-form `evictionHard: memory.available<N%` is already supported upstream [doc-node-pressure-eviction.md L200 allows a percentage or absolute, not both]). Constraint: Allocatable must still fit the u7s system pods that are pods (CoreDNS, servicelb, flannel, MariaDB in the gate); mayor-9ygmh found 256/160 Mi reserved made `mariadb-0` unschedulable on a ~947 MiB node.

## Unclear (needs operator or measurement)

1. Whether any Conformance run has ever been done on a 1 GiB node: no evidence found in this audit; the suite's own pod set + u7s system pods vs ~565-760 MiB allocatable is untested.
2. Whether an early MemoryPressure taint is acceptable *during* a Conformance run on a small node (framework treats it as node-unavailable, row 9/framework coupling).
3. Whether the kubelet systemd unit's `oom_score_adj` and `MemorySwapMax` are set by u7s; unit files not audited here.
4. Why k3s image-GC "CPU storm" occurs (upstream retries every 5 min); out of scope, see lewl1.3.
5. Eviction latency is 10 s poll, uncovered by `kernelMemcgNotification` on cgroup v2; whether a PSI-driven trigger (class I, u7s-owned) is wanted is an operator decision for mayor-lewl1.4.
